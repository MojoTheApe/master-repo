# Project workflow

Use GitHub for tasks, code, reviews and checks; Master Repo for the common standard;
Task Tracker for visibility. This skill guides the active agent. It does not
schedule agents, create permissions or install another workflow system.

## Read the applicable instructions

Start with project `AGENTS.md` and the task's current requirements. Follow its
reading map to local workflow, product knowledge, check commands and delivery.
Where `delivery.json` pins Master, obtain that exact reviewed revision and read
`standard.md` plus the relevant profile. Do not assume the installed skill contains
a Master checkout or that the latest branch is the project's adopted standard.

The canonical skill is `.agents/skills/project-workflow/` in Master Repo:
https://github.com/MojoTheApe/master-repo .
AI Skills distributes a verified mirror. Edit the source and affected references
together; do not independently edit the mirror or install it into other
environments merely to test a change. Skill updates do not change consumer pins.

Read only what the task needs. If a source is unavailable, use checked-in guidance
for independent work and identify the missing dependency for dependent actions.

## Carry a task through

1. Read the complete Issue and prior decisions. Check whether the result already
   exists or another participant is working on it. Separate requirements from
   progress notes; assess changed requirements and relevant source changes.
2. Record the implementer and a short plan in the existing task. Use an isolated
   task branch and the project's supported naming/reference fields. Follow any
   already adopted local ownership procedure; do not invent a new one.
3. Implement the agreed result and update affected product knowledge. Group related
   fixes into a meaningful ready submission using the existing
   [verification](references/verification.md) plan and useful intermediate feedback.
4. Link the ready PR and Issue both ways. Invoke a separate non-implementing
   subagent to review the actual head/base, full scope, changed files and existing
   evidence. Self-review under another label is not independent review.
5. Address findings on the task branch. Follow the local return/handoff procedure
   where one exists. Obtain current relevant review and checks for changed content.
6. Integrate and complete the project's authorized delivery with its existing
   tools. Record the actual result and remaining problems; do not close partial
   work or call source merge a deployment.

Use one supported final admission check; if it includes linkage or other checks,
keep early feedback without immediately repeating those service actions. Respect
actual branch protections and distinct delivery requirements. Reviewers inspect
valid evidence and add checks for findings, missing coverage, changed inputs or
unresolved risk; another agent/session does not reset unchanged test evidence.

Avoid duplicate agent-requested runs. Existing GitHub events still start their
configured checks; do not edit workflows/settings to enforce this guidance.
Compatible prose can be clarified locally without pin/helper upgrades. Note
concrete unnecessary repeats or confusing steps using existing Issue/PR/run links.
Do not create extra demonstrations, scheduled audits or a new register merely to
prove a prose edit. Audit/configuration work follows its explicit scope and existing
authorization, without a routine new approval. Do not claim unmeasured savings.

A changed main needs compatibility assessment, not an automatic rewrite of
unchanged work. A task's age alone needs no extra permission. On an uncertain
write, inspect the actual Issue/PR/target before retrying. Keep useful history.

Accept the owner's direct confirmation that an agent stopped; an unavailable host
does not require repeating that confirmation. Use the compatible selected guide for explicit phase-preserving `pause stop`
with the actual acting identity, stopped fact and durable handoff; preview then apply. Preserve work references,
history and dependencies; mark uninspected local content unknown. Paused and
Blocked are different: correct a conservative stop-added flag only through a
supported command and only when no real obstacle is hidden. Verify the released
assignments. Preserve the native category/phase, source/history, frozen selection,
Stage and requested product delivery. Resume requires a genuinely free slot, fresh
authority and current scope/main/source/dependency/independence checks; otherwise
remain Paused with a reason. A frozen Coordinator resumes in a genuine new session
before its combined Reviewer. Retained reviews are history, not a new approval.
Read Master docs/task-pause.md and the compatible selected Tracker guide; publish
readers/all writers before owned idle outer8 activation. Upstream publication,
exports, pin and skill updates never activate live state. Older consumers keep
their adopted procedure; do not rename Todo-moving stops as phase-preserving Pause.

Independent tasks may use available real agents in isolated worktrees when
delegation is authorized. Coordinate overlap and expensive checks in the existing
task. Report serial work honestly when parallel sessions are unavailable. Use a
different final reviewer; if unavailable, report that limitation.

## Know what is finished

Deliver process changes separately from the consuming product, regardless of its
installation/deployment profile. Instructions and isolated agent/task tooling have
their own checks and delivery. A verified process-only update does not publish an
otherwise unchanged installer, deploy the application or publish an n8n workflow.
Assess the complete scope and actual product/build/install/update inputs; a path
or label alone cannot establish isolation. Split mixed changes and preserve explicit
product publication requirements. Use the exact supported process proof and normal
admission; never manufacture a source-only completion waiver or cancel an existing
delivery request. Read Master's `docs/process-product-separation.md` for the global
boundary and compatibility order.

For a pinned isolated_verification1 outcome, use the existing process-support
command's bounded proof and supplemental independent assessment after ordinary
main admission. Verify original scope/review/acceptance and the exact successful
official manual workflow attempt/jobs. Syntax alone proves eligibility; inspect
indirect product/build/credential effects. Preserve the pending receipt in history
and actual assessor identity without taking over the original developer. Unknown,
mixed or explicitly requested publication outcomes retain product delivery.

Read the project's completion condition before implementing. Source-only work can
finish at checked main integration. Product changes in a service need verified
delivery; product changes in a package need its required release and installation
check. A publication-specific task
requires publication proof. Use the project's real target and supported evidence.

Continue already authorized integration/delivery without another routine approval.
Preserve separately required local authorization and explicit source-only scope.
If blocked, record the concrete cause and next action on the original task.
Do not infer an installation, deployment or approval from a status label.

The Tracker shows recorded work. Queue length, reserved capacity and running
agents are different; use available confirmed data and show unknown as unknown.
Archive preserves history and does not itself complete or reopen work.
Unfinished review stays in Review. Genuine approved waiting work appears in
Delivery as Ready for integration, preserving the native approved key and current
admission rules. Waiting age uses the actual current approval timestamp; unknown
history stays unknown and never becomes active work time. A paused ready task
retains Delivery. Read Master's docs/task-lifecycle.md for the common rule.

Genuine author corrections wait in Backlog as Needs fixes (native To Do). Only
actual implementation ownership shows Fixing in In Progress. Preserve genuine
origin through supported stop/takeover/pause/resume; fresh handoff ends the cycle
and needs independent review. Done and explicit Paused win. Old missing origin
stays neutral and a claim never invents current activity. Use selected native
owned return/reclaim procedures; compatible legacy Reviewers use `return-for-fixes`
with their actual observed identity and durable report, retaining the same pending
operation after an uncertain write. Never edit private state to create a status.
Source corrections from Delivery preserve frozen intake and Stage; integration-only
findings do not return all members, and publication-only failures remain Delivery.

The active Coordinator continues corrections of the owner's already selected task
set when capacity/admission permit, without another routine approval. New
unselected work, explicit pause resumption and materially changed outcomes retain
actual owner decisions. A free slot never launches an agent or restarts a stopped
run. Source approval alone is no integration permission; already authorized
integration carries through actual required delivery. No scheduler, new ordering,
limits, automatic merge or live policy activation is introduced.

Use the compatible project's selected guide for actual executor activity reporting.
Report your own running, waiting or stopped state with the current owner/session/
claim, once a minute while running. Five minutes without a running/waiting report
means Connection lost after prior confirmation and a frozen work clock;
never-confirmed activity stays Activity unconfirmed; a recorded stop remains while that
owner is assigned. Neither condition releases authority. A foreground wrapper
covers only its actual agent child; do not use a detached perpetual heartbeat or
report for another agent. Missing producers and old runtime gaps remain unknown.
Foreground renewals preserve explicit waiting/stopped modes. Resume running only
through an explicit owner report or an actual new launch.
Read Master's `docs/executor-activity.md` when adopting this common support.

Ordinary knowledge or working-data capture does not become an engineering task
for every save. Changes to rules, automation or product behavior use the development
process. Existing projects with a selected capture mechanism retain that procedure.

## Set up or update a project

For a new repository, read the chosen Master's `docs/adoption.md` short setup
procedure: product description, local commands, completion condition, common
instruction reference and connection to the existing Tracker. Verify the real
board; a local file alone does not connect it. Do not promise a registration mode
the current Tracker does not support.

For an existing project, update only what the task requires. Preserve local tests,
system/runtime knowledge, history, data and deployment controls. A shared
instruction update does not automatically select new execution policies or
upgrade clients. Use [instruction ownership](references/instruction-ownership.md)
when changing shared rules, templates or skill distribution.

Keep existing data/release repositories as the parent's related resources when
that is their actual role. Follow parent delivery and resource-local controls;
do not invent separate adoption, active tasks or completion from a resource link.

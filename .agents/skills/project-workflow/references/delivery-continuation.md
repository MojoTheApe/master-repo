# Continue selected integration through verified delivery

Follow the exact adopted standard and project runtime runbook. One explicit request
to integrate and deliver selected tasks authorizes the whole maintained chain:
independent combined review/checks, optional stage, admitted main merge, project
release/deploy, verification and Tracker receipt. Do not insert a routine second
owner approval after main. Starting development alone ends at Approved in execution
v2/v3; a source approval is neither merge nor deployment authorization. Preserve any
explicit local separate approval or missing access as a concrete blocker.

For compatible runtime/package batches, persist the already-authorized permission
with `batch begin --deliver --delivery-workflow PATH --delivery-job EXACT_NAME`,
using the actual maintained producer. Omitting it retains ordinary integration;
resuming a batch or an arbitrary main push cannot add permission.

Before main, identify the actual adapter/CI, configured target, exact revision/task
handoff, verification and recovery. After merge continue using that mechanism.
Tooling/local and explicitly n8n-source scope completes at the admitted reviewed
merge; do not invent a deploy for it. Package/VPS/ordinary n8n needs real delivery.
A skill directs the active agent; only a configured project mechanism continues
in the background after chat ends. Never claim instructions create executable CI.

Keep a durable candidate/target/task/run record. Serialize target mutations and
prevent stale releases overwriting newer ones. Resume idempotently from persisted
state; after a receipt-write failure reuse valid deployment/verification proof and
retry the receipt rather than creating another release. Do not convert stage/CI
proof into production/package acceptance. Preserve actual installation/update,
workflow publication, behavior, backup and recovery requirements.

A trusted project CI may use exported `tracker_delivery_receipt.py resolve` and
`record` with a same-repository token and portable helpers; it needs no private
engine read token. Follow the exact pinned guide. Resolve requires successful main
CI and the genuine per-task Merged handoff. Exit 75 is pending and needs bounded
retry/resume. The actual configured native verification job emits the exact
`TRACKER_DELIVERY_RECEIPT` log proof only after real acceptance. The recorder
revalidates authorization, exact merge/tasks/target/policy and native job/log before
CAS. An artifact manifest alone is insufficient.

Record successful delivery with the exact pinned Tracker command against the real
merged tasks/revision, current policy and configured target. Retain report/run and
artifact references, read back completion, and close only fully satisfied scope.
If delivery or receipt fails, keep the task unfinished, retain evidence and report
the concrete next action. Resume under existing authorization; ask only when a real
missing decision/access boundary prevents continuation. Consumer upgrades, service
publication and global skill installation remain separately scoped operations.

Pending authorized target delivery blocks later integration to that target, while
source work/review can continue. Explicit owner abandonment uses the supported
`batch delivery-cancel` with real retained Coordinator ownership and a decision
report; retain unfinished tasks/receipts/history and resume via a reviewed fix
batch. Never silently cancel a pending delivery to free the target.

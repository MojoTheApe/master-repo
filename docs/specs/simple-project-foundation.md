# Simple shared project foundation

## Description

Give different projects one understandable documentation structure and a small
shared development foundation. Keep delivery and operational details local.
The owner authorized preparation and implementation on 4 November 2026 after
reviewing the ACL workflow. ACL is evidence, not a template to copy wholesale.

## Specifications

### Scope

1. Shorten the primary standard to ordinary work, common guarantees and clear
   links. Preserve detailed supported contracts and dated history as references.
2. Define the common document map: README, AGENTS, current product, engineering
   context, development workflow, verification, runtime delivery/recovery,
   specifications and meaningful change history. Explain what belongs in each
   and when to update it; small tasks stay in Issues, larger specs are linked.
   Reuse the existing repository/system/runtime layout and preserve local knowledge.
3. Make the existing simple preset the normal new-project CLI path when no route
   or preset is explicitly selected. Require explicit role and completion rather
   than guessing them. Keep delivery profile explicit, allow deliberate Stage and
   capacity choices, preserve explicit batch choices and legacy-execution behavior.
   Remove the accidental implicit five-worker batch path from ordinary new setup.
   Existing descriptors, upgrades and consumers retain their current behavior.
4. Describe gradual project workflow development: inspect the need, recommend one
   suitable option with costs, implement an authorized bounded change in the same
   project, align instructions/configuration, verify relevant behavior, record the
   outcome and retain recovery. Generalize only genuinely shared improvements.
5. Update generated starting guidance and the canonical Project Workflow skill.
   Clarify historical adoption text and remove project-specific requirements from
   generic delivery recommendations without deleting useful historical context.

### Boundaries

No ACL migration, Tracker behavior/UI change, engine pin change, optional policy
activation, live state mutation, installer/deployment, global skill installation,
new reporting system or automatic fleet upgrade. Do not weaken independent review,
accepted scope, product delivery, security, data preservation or actual ownership.
Tracker already supports the selected simple/direct mechanism; new test-only
completion and manual-recovery improvements are separate Tracker work.
Standard version publication and consumer adoption are separate outcomes; this
task follows Master's reviewed-merge source completion. The maintained AI Skills
mirror distributes approved canonical skill changes through its existing route.

### Acceptance

- A reader can identify mandatory common rules, local choices and optional
  references without reading historical protocol migrations.
- The document map names one authoritative location for each responsibility and
  distinguishes specifications, implemented behavior and execution history.
- New CLI setup selects simple/direct without an implicit batch when role and
  completion are supplied; incomplete intent fails clearly before target writes.
  Explicit application/batch, Stage, capacities and legacy selection still work;
  existing upgrades and product completion obligations remain unchanged.
- Generated guidance provides the same structure and workflow evolution advice;
  real generated examples retain source-owned Tracker contracts and local knowledge.
- Existing specifications/history remain accessible. No runtime or consumer was
  changed to demonstrate the standard.
- Relevant behavior regressions, full Master unit suite, descriptor validation,
  link checks and independent review pass; actual merged-main checks are verified.

### Delivery record

Track implementation in the linked Master Issue and PR. Record current source,
checks, independent review and actual merge there, without claiming publication,
consumer activation or measured time savings from source changes alone.

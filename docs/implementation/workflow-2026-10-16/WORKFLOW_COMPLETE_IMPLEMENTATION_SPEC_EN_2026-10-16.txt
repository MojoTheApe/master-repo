COMPLETE WORKFLOW IMPLEMENTATION SPECIFICATION



Master Repo, Task Tracker and consumer projects
Version 1.1 | 16 October 2026 | English handoff for the implementing agent

Build a coherent shared workflow for existing and future projects. Preserve the owner’s original WFO-01 through WFO-29 goals, repair the audited correctness gaps, and complete publication, service activation and applicable consumer adoption. The final system must be understandable, evidence-driven and usable without reconstructing the design from prior chats.



What this document controls

This is the consolidated implementation scope. It incorporates the first Russian technical assignment as Task 02 and supersedes its exclusions only in the later tasks that explicitly add those capabilities. If Task 02 has already been implemented when work begins, verify its acceptance evidence and perform only the missing delta.

The original goals remain required. Simplifications in this specification concern implementation mechanisms and dependency order. No WFO outcome may silently disappear, remain an indefinite experiment, or be marked complete merely because a design document exists. Separate risk decisions are recorded near the end.



How the implementing agent should proceed

- Start with Task 01, then select ready work from the prerequisite and parallel-execution tables. Task numbers organize the scope; dependencies determine readiness. Use small reviewed changes inside each task; do not build one unreviewable cross-repository PR.

- Follow each repository’s actually adopted rules and preserve its local controls. When commissioned to implement, continue within the assignment’s authority; apply its existing merge and maintained-delivery authorization rules without inventing repeated routine confirmations.

- Keep one implementation ledger with status, related WFO IDs, actual Issues/PRs, test evidence, source release, deployed revision and consumer activation. Task numbers here are planning IDs, not GitHub Issue numbers.

- Report an external access or product decision blocker precisely and continue independent work. Do not downgrade completion requirements, fabricate receipts or hide unfinished adoption to obtain a green report.



Definition of a finished system

All mandatory task acceptance criteria pass; compatible Master and Tracker releases are published; the actual shared service is updated; every inventoried repository has a verified applicable disposition; new-project onboarding works; and the final end-to-end and recovery checks pass. A merged PR, published package or installed skill alone is not sufficient.

The Russian owner roadmap is a separate short explanation of this same sequence. The implementation scope is contained in this document and its accompanying criterion ledger, with immutable source references for verification; previous conversations are not required.

Target architecture and common guarantees

========================================================================

Owner | Final responsibility

Master Repo | Normative common policy, profiles, descriptor intent, templates, conservative init/upgrade and canonical Project Workflow skill.

Task Tracker | Executable contracts, claims, transitions, reviews, admission, evidence validation, portable technical export, CLI, service and read-only UI projection.

Consumer project | Product requirements, source, actual check commands, selected route and completion target, local delivery mechanism and operational safeguards.

AI Skills | Original library-owned skills and a verified immutable mirror of the Master-owned workflow skill.

Related resources | Typed links to an owning project, optional observed resource information and delivery attribution; no duplicate task queue by default.

Keep Master and Tracker separate. Keep delivery.json as project intent and tracker/config.json as its validated executable adaptation. Generate or mechanically validate their relationship from one technical contract; do not independently author the same rule in three places.



Independent project choices

Repository role, integration route, Stage, execution capacities, delivery profile and required completion are distinct choices. Roles cover applications, shared tools/libraries, research, knowledge, application data and release storage. Delivery retains VPS, package, n8n publication, n8n source-only, local manual-pull and tooling semantics. A role suggests defaults; it never grants a review or verification bypass.



Invariants across every task

- Bind readiness, review and completion to accepted requirements and exact applicable source/policy/target. A journal exemption exists only under its explicitly adopted contract. Changed requirements invalidate current completion, not immutable prior delivery history.

- Preserve actual ownership, independent review, CAS state writes, pending-operation recovery and complete applicable coverage. A one-member batch is valid; never wait for an arbitrary minimum of five tasks.

- Separate source review from combined-candidate verification. Disjoint paths, unchanged branch names, separate green source runs and prose assertions do not prove semantic compatibility of a combination.

- Derive category/status/activity from canonical evidence. Never create another manually synchronized lifecycle. Progress observes execution; final receipts establish completion.

- Archived visibility and accepted outcome are separate in the final contract. Cancellation/rejection is not success. Historical exceptions remain bounded and visible; no current-body rehash masquerades as old acceptance.

- A released capability, consumer pin, explicit activation, running service and verified real outcome are separate facts. New readers precede incompatible new writers and state. Unknown support fails explicitly.

Default architecture: extend the existing state, exports and maintained producer mechanisms. No new database, universal deployer, central orchestrator, retry daemon or general resource graph is required.

Dispatch and integration rules

- Use one coordinator, up to two implementers and an independent reviewer as a practical four-agent arrangement. Available agent slots do not grant repository work/review capacity. Existing reservations and local rules prevail; a legacy shared slot cannot be bypassed by spawning agents.

- Give each implementer an isolated worktree/branch, exact task/subtask, declared file ownership, pinned interface/base and acceptance evidence to return. The coordinator owns the ledger and resolves overlap before dispatch; a subagent report alone does not establish acceptance.

- Assign one implementation owner at a time to shared schemas, completion evaluation, ownership transitions and export interfaces. Agree interfaces before dependent parallel coding. Changes to the same files or contract require coordinated integration even in separate worktrees.

- Serialize integration, publication and deployment per repository or target under actual reservations. Verify the combined current candidate. The approving reviewer must not have authored those changes; do not substitute several source approvals for required combined-candidate verification.

- Coordinate CI dispatch per candidate. Workers run relevant local checks; reuse hosted evidence only under the adopted proof rules. Prevent duplicate full-suite submissions by different agents, preserve mandatory checks and use the durable retry budget once available.

Parallelism may shorten waiting while increasing total agent or runner work. Track elapsed cycle time and aggregate consumption separately. It is not a savings guarantee or permission to weaken review, expand capacities or skip delivery acceptance.

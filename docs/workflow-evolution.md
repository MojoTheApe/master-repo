# Develop a project's workflow gradually

## Start from its result

At project setup, establish what it does, where it runs, what checks demonstrate
success, what finishes a task, and how failed changes/data can be recovered.
Use known repository facts and owner instructions; ask only for a missing material
decision. Record the short result in the existing WORKFLOW and runtime documents.

Recommend simple/direct work first: task, implementation, independent review,
integration, required delivery, Done. The preset is a starting configuration, not
a safety assessment. Choose Stage explicitly when risk needs an isolated target;
test destinations and side-effect controls are needed before customer-impacting
automation runs. Direct delivery can use Stage. A package still needs actual
publication/install acceptance; a service or runtime n8n workflow still needs
verified target behavior. A small task does not weaken those obligations.

Select batches when combined changes need coordinated integration, and parallel
capacity when real independent executors are useful. Record the reason in the
setup task. Do not create extra environments or a fleet-wide process merely
because a preset or ACL example has them.

## Improve from an actual problem

1. Inspect the existing task/run evidence and current project rules. Describe the
   concrete problem and desired result; distinguish facts from suspected causes.
2. Recommend one smallest useful change, its benefit, extra work and meaningful
   tradeoffs. Give alternatives only when they represent a real owner decision.
3. Use the current task or a linked process task for the authorized scope. Existing
   authorization carries through routine implementation; seek a new decision only
   for changed outcomes, access, cost or an unapproved operational boundary.
4. Change instructions and actual configuration/tools together where required.
   Keep current requirements, data, history, delivery obligations and live owners.
   Follow the selected engine's migration/recovery procedure for executable changes;
   a prose edit cannot activate unsupported behavior or change durable state.
5. Check the changed behavior and independently review it. Reuse valid evidence;
   observe the next ordinary task when appropriate instead of inventing production
   work. Record what is actually verified and any remaining adoption separately.
6. Write a short process-history entry with the reason, result, task and recovery
   reference. Stop at the accepted improvement; do not add a permanent new report.

For manual merges, uncertain writes or local-to-Git recovery, inspect the real
source/target first, preserve other work, identify the accepted revision and reuse
valid delivery evidence through the supported recorder. Keep failures and their
resolution in the original task. A missing record alone does not justify replaying
a completed deployment. Missing supported recovery is a tooling task, not permission
to fabricate Done. Push tested local work before handoff and name anything still local.

## Promote only reusable lessons

Project-specific commands, product constraints and release steps stay local.
A principle useful across projects can become a Master rule or optional profile;
executable shared behavior belongs in Tracker. Update their actual compatible
support and canonical skill when affected. Common rules retain truthful completion,
independent review and data/security safeguards; local choices may add controls.

Existing projects do not adopt a changed standard automatically. Preserve their
pins and working process. Compare actual differences, choose a bounded migration
only when useful, and verify it under the project's current rules.

# Accepted-scope completion

An explicit completion policy binds current success to the requirements that were
actually reviewed or accepted. Tracker owns its executable assessment, receipt
provenance, commands and durable activation. Master selects the intent and checks
that the generated configuration and exact export agree.

## Select the contract

Schema-2 descriptors may explicitly select:

```json
{"workflow": {"completion_policy": {"schema_version": 1}}}
```

The generator mirrors that object as `completion_policy` in `tracker/config.json`.
The existing top-level `completion`, delivery target, required checks, execution
capacity and Stage choice retain their meanings. Selection does not turn a runtime
or package task into reviewed-merge work. No completion policy is selected by
default, and a normal upgrade preserves its previous choice.

Use `standard.py init --completion-policy` to include the explicit contract in a
new draft. `standard.py upgrade --completion-policy` prepares its three-way source
upgrade using the genuine recorded old template. Both retain the exact compatible
Tracker guide and portable assessment; unsupported or mismatched exports fail.
Preview before applying, independently review the resulting local project change,
and keep project-owned system/runtime knowledge and operational controls.

## Activate separately

Source configuration, a new engine pin and an installed skill do not activate the
contract. Read the exact exported `docs/repository/COMPLETION_POLICY.md` (standalone
Tracker exports use `docs/COMPLETION_POLICY.md`) for current commands and protocol.
It defines owned idle activation, the durable state fence and compatible writer
refusal; the source guide is not replaced by the latest online branch.

Follow that guide's activation order when task context is also new to an existing
project: select and activate the two policies in separate reviewed configuration
changes. Do not leave both selected but unactivated. New-project initialization
uses the exact engine's documented execution migration before completion adoption.

Publish supporting immutable engine/export and compatible standard releases,
verify the actual service reader, then perform the reviewed consumer upgrade and
owned state activation. Inspect all actual CLI, portable receipt, CI and service
writers before cutover. Keep unresolved ownership, pending operations and delivery
obligations intact. Verify old incompatible writers refuse rather than dropping
the new scope contract. Recover with a compatible reader and preserved state,
not an older reader that cannot parse accepted newer history.

## Interpret the evidence

Accepted scope comes from genuine review/acceptance or the frozen batch member.
Never hash today's Issue at merge and describe it as previously reviewed. Changed
requirements invalidate current completion while preserving immutable earlier
delivery history; permitted terminal journals follow only their adopted contract.
One shared assessment drives task views, dependency/release readiness and receipt
writers. A recorded source merge, current successful delivery, changed requirements,
pending/failed delivery and unverified legacy scope remain distinct outcomes.

The activation preview can retain matching original proof with provenance. Unknown
old scope remains unverified under the activated contract and cannot satisfy new
dependencies. Preserve historical acceptance within its exact original bounds;
no fabricated current-body backfill or expanded manifest may create success.
An explicit reopen remains a separate action. Activation does not automatically
reopen Issues or roll back dependents that already started.

This contract preserves current Archive semantics. A retention/outcome redesign,
modern direct-route adoption and verified-publication completion are separate
versioned changes. Record source, publication, reader, consumer activation and
actual accepted behavior separately in the implementation ledger.

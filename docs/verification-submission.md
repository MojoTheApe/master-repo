# Submitting verification work

Keep the verification plan in the project that owns the product commands,
platforms, installers and delivery obligations. Select it by the complete changed
risk and the adopted proof capabilities. A common standard or newer skill cannot
remove a required check or expand an existing collector's coverage.

## Intermediate feedback and ready candidates

| Purpose | Project-owned plan | Required result |
| --- | --- | --- |
| Intermediate author feedback | An explicitly named fast plan with its actual commands, platforms and omissions | A result named, for example, `Fast feedback`; missing full coverage stays visible |
| Ready handoff or final admission | The full applicable plan, including all required product/platform jobs or genuinely supported original evidence | The existing full aggregate and every required admission check |
| Combined integration or delivery | The actual combined candidate and separately required target/package acceptance | Current composition review, applicable integration checks and real delivery proof |

The example fast name is not a generated product check. Each project records its
real names and commands before enabling the plan. Keep fast and full results
distinct; a fast success, skipped full job or renamed check cannot satisfy the
full gate. Unknown, mixed or unclassified changes require full applicable coverage.
Changing a plan name is not a new verification purpose or a fresh retry budget.

## Master source plan

Master's checked-in workflows provide these actual results:

| Native check | Feedback and coverage |
| --- | --- |
| `tracker-link` | Early metadata feedback: linked local Issues exist; it does not test source behavior |
| `skill-impact` | Early metadata feedback: the canonical skill impact assessment is present; it does not test the skill or consumers |
| `validate` | Full source unit suite, descriptor validation and local documentation links |
| `portable-runtime` | Canonical exported helper fixtures on Python3.9 without a private engine |

The two source checks run on opened, synchronized and reopened PRs, including
drafts, and on every main push. Unknown and mixed source changes
receive the same full coverage. Metadata edits run the separate metadata workflow
without restarting source checks. Source cancellation is limited to the same PR;
each main run has a distinct concurrency identity and is retained.

Marking an unchanged draft ready runs metadata validation without submitting a
duplicate full suite. Ready admission still requires both actual full source
checks for the current candidate. Changed relevant inputs/composition or missing
proof require applicable fresh verification; the draft transition cannot waive
it. See the [native PR event contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).

These existing names remain the admission names. Metadata feedback cannot replace
either full source check. A changed technical export contract additionally needs
the maintained exact-source paired compatibility gate before publication, with
real previous released-source upgrades; ordinary source checks alone do not
prove that pair. Record the actual changed contract or missing proof as the reason
for that heavier publication check. No product installer or consumer deployment
is launched to test Master templates.

Group related local corrections on the same owned task branch before submitting
a meaningful new candidate. Preserve checkpoints and useful early hosted feedback;
there is no fixed waiting interval. Keep one task per ordinary execution source
PR and retain the original branch for author fixes. Inspect existing author/native
evidence before repeating unchanged checks. Reviewers add checks for a finding,
missing scope or an unresolved concern.

## Launch decisions and native evidence

Record why new expensive verification is needed: changed relevant content or
inputs, missing platform coverage, an actual merge composition, expired or invalid
proof, a permitted diagnosed transient retry, or required fresh delivery acceptance.
Bind an observed decision to its actual candidate and native run. Historical
reasons inferred from commit text or incomplete logs remain labelled inferred or
unknown. A reason string never grants permission or resets a durable budget.

Separate PR metadata/linkage checks and their concurrency group from code checks.
Body edits keep metadata validation without restarting unchanged heavy work.
Use PR content events for source suites and retain actual integration/main push
evidence; avoid duplicate heavy push and PR suites for the same source event.
Cancel only superseded work for that same PR. Preserve every required integration,
main, Stage, installer and platform result and the existing job timeouts.

Use adopted semantic compatibility evidence for an unchanged Approved source when
the pinned engine supports it. Unrelated main movement does not require an empty
commit or a meaningless merge just to restart CI. Actual conflicts, changed scope
or inputs need reconciliation; disjoint files alone are not compatibility proof.
Native branch protection and independent combined review still apply.

For an unchanged candidate, use supported native retry operations. Where a durable
retry policy is already adopted, follow it. The existing common collector's single-attempt support
cannot infer coverage for successful jobs omitted from a partial rerun. Preserve
a project's stronger reviewed adapter; otherwise use a supported bounded fresh
attempt or stop. Never reinterpret an instruction-only skip as reuse or broaden
an exhausted partial retry into repeated full runs.

Measure first useful feedback, full-cycle latency and actual execution intervals
separately on comparable ordinary workloads. Parallel execution minutes are not
wall-clock latency. Preserve missing coverage, workload/environment changes and
unavailable billing in both human and machine reports; fewer runs alone establish
neither lower net charges nor a fleet saving. No paid demonstration or recurring
analytics service is required.
